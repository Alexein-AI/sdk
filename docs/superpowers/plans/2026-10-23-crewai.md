# `twinmemory-cli init crewai` Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `uvx twinmemory-cli init crewai`, `create crewai <name>` and `doctor` for CrewAI, writing a `memory.py` that runs CrewAI's own memory machinery on twin memory, for classic and JSON crews.

**Architecture:** A second framework in the existing Python `twinmemory-cli` (`packages/python`). A new template, `templates/crewai/memory.py.tmpl`, holds `TwinMemory` (a subclass of `crewai.memory.Memory`) with the end user held per run in a `ContextVar`, plus a tools-only part. `scaffold.init` dispatches on the framework; CrewAI gets its own project detection, version guard, target directory and next steps; `create` and `doctor` learn CrewAI the same way.

**Tech Stack:** Python 3.10–3.13, crewai 1.15.x, the `twinmemory` client (from `vendor/`), pytest, ruff, pyright.

**Spec:** `docs/superpowers/specs/2026-10-23-crewai-design.md`

## Global Constraints

- CrewAI minimum `1.15`; tested range recorded as `CREWAI_TESTED = "1.15"` (the newest minor the release was tested with). Newer minor installed → a warning, not a stop.
- Python `>=3.10` (crewai itself requires `<3.14`).
- The end user comes only from the run's inputs, key `user_id`, never from a tool argument or the model.
- Every kickoff must carry `user_id`; a run without it raises before any task runs.
- The client is made as `Memory(fail_open=not STRICT, integration="crewai", timeout=TIMEOUT)`.
- Settings at the top of the written file: `FAST = {fast}`, `STRICT = False`, `MAX_CHARS = 4000`, `TIMEOUT = 10.0`.
- File header line: ``Generated by `twinmemory-cli init crewai` (twinmemory-cli {version}).`` (and `init crewai --tools-only` for that preset).
- Written files pass `ruff check --isolated --select E,F,I,B,UP,SIM,RUF,W` and `ruff format --isolated --check` at the default 88 columns, run from the project's folder.
- No edits to the developer's `crew.py` or `crew.jsonc`; `init` prints the lines.
- Presets for CrewAI: default (automatic) and `--tools-only`, plus `--fast`. `--nodes-only`, `--async` and `--graph` are refused for CrewAI with exit code 2.
- Install for `init crewai`: `twinmemory>=0.2` only.

## Review Focus

1. **A kickoff without `user_id`**, or with `""` / `None`: the crew must not run, and the error must say to pass `inputs={"user_id": ...}`. Test in Task 2 (`test_a_run_without_a_user_stops_before_any_task`).
2. **A run that raises part-way, then a run for a different user in the same process** (a long-lived server): the second run reads and saves only its own user's memory. Test in Task 2 (`test_a_failed_run_leaves_nothing_behind`).
3. **Concurrent runs for different users on one `TwinMemory`** (`kickoff_for_each_async`, and `akickoff`): no recall or save crosses users, including saves on CrewAI's background pool. Test in Task 2 (`test_concurrent_runs_never_mix_users`).
4. **A newer CrewAI than tested**: `init` and `doctor` warn and carry on; an older one stops `init`. Tests in Task 3 (`test_a_newer_crewai_warns`) and Task 5.
5. **Empty task output and delegation output**: nothing is saved (no empty items sent). Test in Task 2 (`test_an_empty_result_saves_nothing`).

### Task 2: The written file — `templates/crewai/memory.py.tmpl`

**Files:**
- Create: `packages/python/src/twinmemory_cli/templates/crewai/memory.py.tmpl` (parts `auto` and `tools`, marked as the LangGraph template marks `nodes` and `tools`)
- Modify: `packages/python/pyproject.toml` (dev group: `"crewai>=1.15,<1.16"`; `uv lock`)
- Test: `packages/python/tests/test_crewai_template.py`

**Interfaces:**
- Consumes: `render(template, parts, values)` from `render.py`; the test helpers `memory()`, `ok()`, `Answer` from `tests/conftest.py`.
- Produces (names in the written file, which Task 3's next steps, Task 4's project and Task 6's docs print):
  - `class TwinMemory(crewai.memory.Memory)` — made with `TwinMemory()`; overrides `recall(query, scope=None, categories=None, limit=10, depth="deep", source=None, include_private=False) -> list[MemoryMatch]`, `remember(content, ...) -> MemoryRecord | None`, `remember_many(contents, ...) -> list[MemoryRecord]`, `extract_memories(content) -> list[str]` (returns `[content]`, no model call).
  - `twin_memory: TwinMemory` — a module-level instance (what JSON crews reference).
  - `def whose(inputs: dict[str, Any]) -> dict[str, Any]` — pops `user_id`, sets the run's user, checks the key once per process, returns the inputs.
  - `def memory_tools(user_id: str, *, writes: bool = True) -> list[BaseTool]` and `def save_result(user_id: str, output: Any) -> None` (part `tools`).
  - `_memory() -> twinmemory.Memory` (cached client) and `_user` (the `ContextVar[str | None]`) — patched in tests, as the LangGraph template's `_memory` is.
- Behaviour pinned by the spec: recall → twin search (fast per `FAST`), matches best first, at most `limit`, total text within `MAX_CHARS`; 404 → `[]`; memory down → `[]` and a warning. Saves → twin `add` as notes with `author` = the agent role where CrewAI gives one and `session` = one id per kickoff (set in `whose`); stable item ids; memory down → skipped with a warning, `remember` still returns a `MemoryRecord`. Unsupported `Memory` methods (`forget`, `update`, `reset`, `scope`, …): the builder chooses no-op or `NotImplementedError` naming the twin route, but none may act on another user. Constructed with a dummy storage so LanceDB is never built. Failures inside `recall`/saves are logged on the `twinmemory` logger before CrewAI swallows them.
